02 Annotated Stack Table

Every row: the exact technology chosen, why it won, what was rejected, and why. Rows marked critical path sit directly on Register & Pay — the #1-ranked critical workflow (doc §8) — and were the rows the stress test scrutinized hardest.

ComponentExact ChoiceWhyRejected AlternativeRejection Reason
Frontend Next.js (React) — public event page as static/ISR on CDN edge The public event page is read-heavy and, per §1.3, displayed availability may be near-real-time — so it can be served almost entirely from the edge, isolating burst reads from burst writes. Remix Comparable capability; Next.js’s ISR is a more first-class fit for this specific edge-caching pattern than Remix’s rendering model.
Backend framework Fastify — lightweight, no heavy DI container Matches the hosting model on the hot path below; I/O-bound workload (payment calls, DB, email) suits Node well. NestJS Stress-test finding: NestJS’s long-lived DI-container bootstrap fights serverless cold starts, worsening lock contention exactly on the #1-ranked critical workflow (§8).
Hosting — public / low-frequency paths Serverless / CDN (Vercel + Lambda) Browsing, publishing, and the organizer dashboard are genuinely idle most of the year (§7) — elastic capacity avoids paying for constant provisioning. Always-on PaaS for everything (Render/Railway) Pays for idle capacity ~360+ days a year when load is concentrated in a handful of one-hour bursts.
Hosting — checkout / hold-creation hot path Always-on autoscaling baseline (Fargate/Fly.io) + scheduled provisioned-concurrency warm-up This is the #1-ranked critical workflow (§8); a cold start colliding with peak contention was judged unacceptable by default. Opening times are known at publish time, so warm-up is schedulable. Full serverless, same as the public path Stress-test finding: accepting cold-start risk here is a real cost/complexity tradeoff, not a free win, given what this workflow protects.
Database (system of record) PostgreSQL + mandatory connection pooler (PgBouncer / RDS Proxy) Real transactional guarantees (row/advisory locks) for the §1.3 capacity invariant; the pooler is mandatory, not optional. MySQL No meaningful advantage for this workload; Postgres’s native materialized-view support is also more mature for the dashboard read path (§7).
Reporting / dashboard read path Postgres read replica; materialized views refreshed CONCURRENTLY, read from the replica Structurally guarantees reporting reads never compete with checkout writes, satisfying §7’s isolation requirement. Event-driven aggregates in a separate store Stress-test finding: cleaner isolation in principle, but materially higher build cost than the replica already delivers at this scale.
Hold / counter layer Redis — managed, AOF persistence + replication, dedicated instance Native TTL/EXPIRE maps directly onto §1.3’s automatic hold-expiry requirement; keeps the hottest operation off the durable DB. Postgres row locks alone, no separate cache Legitimate if §6’s peak-demand number comes back low — rejected only provisionally, pending that still-open answer. Persistence/replication itself is required after a stress-test finding that an unreplicated restart mid-burst would silently free held seats.
Job queue BullMQ on a second, separate Redis instance Decouples ticket issuance and reminder dispatch from the checkout response and absorbs batch spikes (§7). SQS + Lambda workers A reasonable AWS-native alternative, rejected mainly for consistency with the Node/Redis stack, not a capability gap. Separated from the hold-counter Redis after a stress-test finding that a shared instance let a notification backlog steal capacity-check resources.
Auth — organizer / staff Managed provider (Clerk / Supabase Auth) Organizers and check-in staff need real accounts with roles (§5 AuthZ boundaries) — buy, don’t build password storage, sessions, MFA. AWS Cognito Comparable capability; rejected for developer-experience overhead relative to Clerk/Supabase absent an existing AWS-native stack.
Auth — attendee (resend / cancel / refund) Managed passwordless / magic-link feature (e.g., Supabase Auth magic links) Sits directly upstream of a financial action (refund, §5); still contingent on §6’s open identity-verification question. Custom-built lightweight magic-link system Stress-test finding: cheaper to build, but puts custom token-expiry/single-use/replay code directly ahead of a financial action — too much risk for the savings.
Payments Stripe International reach and ease of integration for both developers (Checkout/Elements handle §5’s PCI tokenization) and customers (localized Checkout, native wallets). PayMongo / Xendit (regional gateways) Don’t cover the international/ease requirement as cleanly and can carry a regional-throughput ceiling into a burst (stress-test finding #4). Local rails (GCash, etc.) remain a separate, still-open question (§6) Stripe doesn’t resolve.
Email Postmark / Resend Tickets and reminders are must-arrive transactional email — deliverability matters more than per-email cost. Handles §7’s rate-aware queued sending for a ~2,000-email burst. Amazon SES Cheaper at volume, but pushes sender-reputation management onto the team — not worth it until volume justifies the tradeoff.
Monitoring Sentry + uptime checker, with explicit alerts on Postgres pool saturation and Redis replication lag/failover A mostly-idle system (§7) doesn’t justify a full APM platform’s cost by default; the two named alerts target the exact failure modes the pooler and Redis-replication decisions exist to prevent. Datadog / New Relic Priced and featured for constant-traffic systems; justified only if the lighter stack proves hard to diagnose during real burst events.

03 Registration & Payment — Sequence

sequenceDiagram
  autonumber
  actor St as Staff
  participant Sc as Scanner App
  participant API as Backend
  participant DB as Postgres
  participant Dash as Dashboard Read Model

  St->>Sc: Scan attendee QR code
  Sc->>Sc: Read signed ticket payload

  alt Online model
    Sc->>API: Send ticket ID for validation
    API->>DB: Verify signature, check status, mark checked-in - atomic
    alt Ticket valid and unused
      DB-->>API: Marked checked-in
      API-->>Sc: Valid - Admit
    else Already used or invalid
      DB-->>API: Rejected
      API-->>Sc: Invalid - Deny
    end
  else Offline model
    Sc->>Sc: Verify signature locally against embedded public key
    Sc->>Sc: Mark checked-in locally, queue for sync
    Note over Sc,API: True single-use across devices is not guaranteed until sync.
    Sc-->>API: Sync when connectivity returns
    API->>DB: Reconcile - flag duplicate checked-in tickets
  end

  API->>Dash: Update live check-in count
  Dash-->>St: Reflected on organizer dashboard

Online: the server checks signature and "used" status together, so single-use is truly atomic. Offline: the device verifies the signature locally with no server round-trip, and single-use becomes a post-sync reconciliation problem rather than a real-time guarantee.
